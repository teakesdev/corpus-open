## Findings

### P2-1 — `w:sym` is silently dropped; a `§`/`¶` written as a symbol character vanishes with no warning

`matterkit/draftdocs.py:435-437` puts `"sym"` in `_RUN_INERT`; `matterkit/draftdocs.py:477-478` then `continue`s past it in `_run`. A `w:sym` produces a real visible glyph (`w:char` + `w:font`) but has no `w:t` child, so it is skipped with no entry in `st.unhandled` and no warning.

Failure scenario, worked by reading: a pro se litigant's draft was converted from WordPerfect (or they used Insert ▸ Symbol) and `Compl. ¶ 59` is stored as `Compl. <w:sym w:font="Symbol" w:char="F0B6"/> 59`. Extraction yields `Compl. 59` after `normalize` collapses the gap. `PLEADING_RE` requires the `¶`, so the pleading cite is never matched: it is absent from the proposition table's cited-source cell, never pin-checked against the complaint, and no `draft-*` warning says anything was dropped. If the containing sentence has another record cite it reads as fully cited — a silent false pass, exactly the class of miss the checker exists to catch. Statute cites are affected too where the `§` is a `w:sym` (`42 U.S.C. 1983` still matches without `§`, so the damage is mainly to `¶`-forms and to any case where the dropped glyph changes the text the patterns see).

Exact edit: in `_run` (draftdocs.py, before the `_RUN_INERT` branch at line 477) add `elif loc == "sym": st.unhandled.add("sym")` (a symbol glyph, like a text box, is content the reader cannot read and must say so), and remove `"sym"` from `_RUN_INERT` at line 436 so it cannot be reached silently. Optionally render the glyph: `w:sym` carries `w:char`/`w:font`; mapping `F0A7`→`§`, `F0B6`→`¶` for the Symbol font would preserve the common cases, but warning alone closes the silent drop.

### P2-2 — the tracked-change refusal and the formatting-change warning scan only document + notes, not styles.xml / numbering.xml / settings.xml

`matterkit/draftdocs.py:579` builds `parts` from `(doc, footnotes, endnotes)` only; both the `_TRACKED` refusal loop (lines 581-585) and the `_FORMAT_CHANGES` warning (line 596) iterate just those roots.

Failure scenario, worked by reading: with Track Changes on, the litigant edits the "Heading 1" paragraph style — Word records this as `w:pPrChange` inside that style's `w:pPr` in `word/styles.xml`. That root is parsed at line 566 but never scanned: `_TRACKED` misses any `w:ins`/`w:del` inside style or numbering parts, and `_FORMAT_CHANGES` misses the `pPrChange`. The reader then silently uses the post-change outline level in `styles.heading_level` (line 674), so a heading can appear, disappear, or change level relative to what the author sees with changes unaccepted — with neither the refusal the README promises for tracked changes nor the formatting-change warning it promises for tracked formatting. Numbering definitions in `numbering.xml` and `footnotePr`/`numStart` in `settings.xml` have the same exposure.

Exact edit: keep references to the parsed roots and scan them — e.g. `styles_root = pkg.part("word/styles.xml")`, `numbering_root = pkg.part("word/numbering.xml")` before constructing `_Styles`/`_Numbering`, then `parts = [r for r in (doc, notes_roots["footnote"], notes_roots["endnote"], styles_root, numbering_root, settings) if r is not None]`. Whether a tracked insertion inside a style part should refuse (consistent with `_TRACKED`) or warn (consistent with `_FORMAT_CHANGES`, since it is property-level) is a judgment call; the minimum acceptable fix is extending the `_FORMAT_CHANGES` scan to these roots so a tracked formatting change outside the document body still warns.
